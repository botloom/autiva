```markdown
# 进化引擎

Autiva 内置了 GEP（基因组演化协议）进化引擎，帮助你持续改进。

## 核心概念

- **基因 (Gene)**：紧凑可复用的演化指令，是自适应行为的最小单元。每个基因包含策略步骤和约束条件。
- **胶囊 (Capsule)**：高阶演化资产，将相关基因与附加上下文打包，通常由高分进化事件自动生成。
- **信号 (Signal)**：从对话中提取的结构化观察结果（错误、性能瓶颈、能力缺口等）。

## 如何使用

当你或子智能体遇到以下情况时，可以调用进化工具：
- 反复遇到同类错误 → 调用 `evolve_query` 查找修复类基因
- 发现性能瓶颈 → 调用 `evolve_query` 查找优化类基因
- 需要新能力 → 调用 `evolve_query` 查找创新类基因
- 想了解进化历史 → 调用 `evolve_query` 查看最近进化事件
- 需要进化推荐 → 调用 `evolve_query(recommend)` 获取推荐基因

### 可用工具

- **evolve_query**：查询基因库和胶囊库，支持按类别、信号类型筛选
- **evolve_apply**：应用选定的基因或胶囊，获取策略步骤和约束条件指导行动

### 进化智能体
```

#### 核心方法

- **`execute(Input, ToolContext)`**：工具执行入口

  5. 调用 `executeSubagent` 执行任务

- **`loadSubagentDefinition(String name)`**：从 `classpath:subagent/{name}/agent.md` 加载定义

- **`executeSubagent(Agent, TaskCall, context, onChunk)`**：
  - 流式模式：`chatClient.prompt().system(systemPrompt).stream().chatResponse()` + `blockLast()`

- **`buildSubagentSystemPrompt(Agent)`**：组装系统提示词
  - 基础：`definition.content()`

## 5. 事件系统（Event）

### 5.1 事件总线

`d:\project\autiva\autiva-desktop\src\main\java\cn\bitloom\agentic\event\EventBus.java`

基于 Reactor Sinks 的全局事件总线（静态字段）：
- `inBox`：`Sinks.Many<AbstractEvent>`（multicast + onBackpressureBuffer），接收外部消息
- `outBox`：`Sinks.Many<AbstractEvent>`，发布 Agent 响应
- `publishIn(event)` / `publishOut(event)` / `inBoxFlux()` / `outBoxFlux()`

### 5.2 事件类型层次

`d:\project\autiva\autiva-desktop\src\main\java\cn\bitloom\agentic\event\`

- **`IEvent.java`**：空接口
- **`AbstractEvent.java`**（`@SuperBuilder`）：字段 `sessionId`
- **`MessageEvent.java`**（`@SuperBuilder`，继承 `AbstractEvent`）：
  - `Type` enum：`USER` / `ASSISTANT` / `TOOL`
  - 字段：`type` / `text` / `finishReason`（null=流式片段, "STOP"=完成, "TOOL_CALLS"=工具调用）/ `toolCalls` / `responses` / `attachments`
  - 静态工厂：`userMessage` / `assistantStream` / `assistantStop` / `assistantToolCalls` / `toolResponse`
  - 内部 record：`ToolCallInfo(name, arguments)` / `ToolResponseInfo(name, responseData)`

### 5.3 EventConverter（双向转换器）

`d:\project\autiva\autiva-desktop\src\main\java\cn\bitloom\agentic\event\EventConverter.java`

**这是唯一同时依赖 Spring AI 和事件类型的类**，起到隔离层作用。

- **`fromMessage(sessionId, Message)`**：Spring AI Message → MessageEvent
  - `UserMessage` → `MessageEvent.userMessage`
  - `AssistantMessage`：
    - `finishReason == "TOOL_CALLS"` → `MessageEvent.assistantToolCalls`
    - `finishReason == "STOP"` → `MessageEvent.assistantStop`
    - 其他 → `MessageEvent.assistantStream`
  - `ToolResponseMessage` → `MessageEvent.toolResponse`

- **`toUserMessage(MessageEvent)`**：MessageEvent → Spring AI `UserMessage`（Agent 输入用）

- **`fromMessages(sessionId, List<Message>)`**：批量转换历史消息

### 5.4 事件流转

```
用户输入 → HomePageViewModel.sendMessage()
         → session.publish(MessageEvent.userMessage)  [inBox]
         → Session.start() 订阅 inBox
         → Agent.runStream()/runBlock()
         → EventConverter.fromMessage() 转换响应
         → EventBus.publishOut()  [outBox]
         → HomePageViewModel.subscribeOutBox() 订阅 outBox
         → processEvent() 分发到 UI
```

## 6. 消息/对话系统的核心数据结构

### 6.1 Session（唯一状态源）

`d:\project\autiva\autiva-desktop\src\main\java\cn\bitloom\agentic\session\Session.java`

`@Data @Builder @NoArgsConstructor @AllArgsConstructor`，是消息处理的核心编排者。

#### 字段分类

**标识字段**：`id` / `agentId` / `userId`

**会话分类**：`sessionType`（`SessionTypeEnum`：DM/GROUP/SYSTEM）/ `respType`（`SessionRespTypeEnum`：STREAM/BLOCK）/ `source` / `parentId`

**元数据**：`model`（`ModelTypeEnum`）/ `title` / `createdAt` / `updateAt` / `sessionState`（`SessionState`：IDLE/GENERATING/PAUSED/STOPPED）

**对话上下文**：`messageCount` / `memoryCursor` / `summary`

**压缩上下文**：`contextCapacity`（默认 40000）/ `compactionThreshold`（默认 0.5）/ `currentContextLength`

**工具上下文**：`activatedToolGroups` / `permissionMode`

**任务上下文**：`tasks`（`List<TaskItem>`）

**计划模式**：`planModeActive` / `planFilePath`

**瞬态字段**（`@JSONField(serialize=false, deserialize=false)`，不持久化）：
- `agent`（`Agent`）
- `messages`（`List<Message>`，Spring AI 消息列表）
- `subscription`（`Disposable`，Reactor 订阅）

#### 核心方法

- **`start()`**：启动消息处理循环
  - 订阅 `EventBus.inBoxFlux()`，过滤当前 sessionId
  - `concatMap` 分发 `MessageEvent`：
    - USER 消息 → `EventConverter.toUserMessage` → `agent.runStream`/`runBlock`
    - 响应通过 `EventConverter.fromMessage` 转换 → `EventBus.publishOut`
  - 完成后设置 `sessionState = IDLE`

- `publish(AbstractEvent)`：发布到 inBox
- `subscribe()`：返回 outBoxFlux
- `stop()`：设置 STOPPED + dispose subscription

#### 内部类 TaskItem

`@Data @Builder`，字段：`id` / `content` / `status`（pending/in_progress/completed）/ `priority`（high/medium/low）

### 6.2 FileSystemSessionManager

`d:\project\autiva\autiva-desktop\src\main\java\cn\bitloom\agentic\session\FileSystemSessionManager.java`

Spring `@Component`，`@Lazy` 注入 `AgentManager`（避免循环依赖）。

#### 核心方法

- **`@PostConstruct init()`**：`loadAllSessions()` 从 `workspace/{agentId}/sessions/` 加载所有 `metadata.json`

- **`create(agentId, source, type, respType, model)`**：
  - 生成 sessionId：`{agentId}-{type}-{source}-{userId}-{timestamp}`
  - 创建目录和 `messages.jsonl` 文件
  - `persistSession` + `activate`

- **`activate(sessionId)`**：
  1. 注入 Agent（`agentManager.getAgent`）
  2. 从磁盘加载最新 metadata（`syncPersistentFields`）
  3. 加载历史消息（`messages.jsonl`，每行一个 JSON 消息，`MessageUtil.deserializeMessage`）
  4. `session.start()` 启动消息循环

- **`fork(parentSessionId, subagentName)`**：创建子会话
  - 继承父会话最后一条用户消息后的消息
  - 用于子智能体执行

- **`store(sessionId, List<Message>)`**：
  - 追加消息到 `messages.jsonl`
  - 发布 `AssistantMessage(TOOL_CALLS)` 和 `ToolResponseMessage` 到 outBox
  - 添加到 `session.getMessages()`

- **`updateSession(sessionId, Consumer<Session>)`**：局部更新 + 持久化

- **`persistSession(session)`**：序列化到 `metadata.json`

#### 持久化格式

```
~/.autiva/workspace/{agentId}/sessions/{sessionId}/
├── metadata.json    # Session 持久化字段（不含瞬态字段）
└── messages.jsonl   # 每行一个 Spring AI Message 的 JSON
```

### 6.3 CompactChatMemory（游标感知记忆）

`d:\project\autiva\autiva-desktop\src\main\java\cn\bitloom\agentic\memory\CompactChatMemory.java`

Spring `@Component`，实现 Spring AI `ChatMemory` 接口。

- **`add(sessionId, List<Message>)`**：
  1. 清理孤儿工具调用消息（如果上一条是 `AssistantMessage(tool_calls)` 且本次无 `ToolResponseMessage`，则移除）
  2. `fileSystemSessionManager.store(sessionId, messages)`
  3. 估算并更新 `currentContextLength`（USER/ASSISTANT 按文本长度，tool_calls 每个 +200，ToolResponse +500）

- **`get(sessionId)`**：返回 `memoryCursor` 之后的消息（`subList(memoryCursor, size)`）
  - 这是游标感知的核心：压缩后 `memoryCursor` 前移，旧消息不再注入 LLM

- **`clear(sessionId)`**：调用 `fileSystemSessionManager.clear`

### 6.4 ViewModel 层

`d:\project\autiva\autiva-desktop\src\main\java\cn\bitloom\vm\HomePageViewModel.java`

Spring `@Component` + `@RequiredArgsConstructor`，注入 `FileSystemSessionManager`。

- **`messages`**：`ObservableList<MessageCard>`（JavaFX 响应式列表）

- **`sendMessage(text)`**：

## 关键架构模式总结

| 模式 | 实现 |
|------|------|
| 统一 Agent 模型 | 主智能体和子智能体都是 `Agent` 类实例 |

| AbstractTool<I> + Toolkit | 泛型 Input record + Spring @Component 容器 |

| 文件系统持久化 | Session 序列化为 metadata.json，消息为 messages.jsonl |
| 游标感知记忆 | CompactChatMemory 基于 Session.memoryCursor |
| GEP 基因组演化 | Gene/Capsule/Signal/EvolutionEvent |
| MVVM 架构 | ViewModel 不持有 UI 引用 |

## 九、关键设计观察与潜在问题

1. **路径体系不统一**：
   - MemorySearchService 和 LongMemoryConsolidateAdvisor 操作 `~/.autiva/agents/default/memory/`
   - MemoryManage*Tool 操作 `~/.autiva/` 或 `~/.autiva/workspace/{agentName}/`

2. **MemorySearchService 硬编码 "default"**：构造函数固定 `memoryDir("default")`，无法搜索其他 agent 的记忆

3. **MemoryManage*Tool 路径解析与文档不符**：AGENTS.md 说 Builder 接受 AgentManager，但实际代码 Builder 是空的，工具内直接用 AppConstants 解析路径，且 `agentName="default"` 时映射到 `APP_DIR`（`~/.autiva/`）而非 `agents/default/`

4. **LongMemoryConsolidateAdvisor 的游标语义**：它读取 memoryCursor 判断"未处理消息数"，但游标由 MemoryCompactAdvisor 推进。若压缩先于整理触发，整理会跳过已被压缩的消息——这是预期行为（避免重复处理），但依赖两个 Advisor 的执行顺序（order=100 先于 order=150）

5. **JournalManager 未实现**：memory/AGENTS.md 第 27-36 行描述的 JournalManager 类不存在，其功能由 LongMemoryConsolidateAdvisor 承担

6. **MemoryCompactAdvisor 推进游标的潜在 bug**：`s.setMemoryCursor(s.getMemoryCursor() + messages.size())` 中 `messages` 是 `request.prompt().getInstructions()`，这是**当前请求的所有指令**（含 system prompt 注入的内容？需验证），可能高估游标推进量。但根据 Spring AI 的机制，instructions 通常只含对话消息，应该安全

```java
    public static void publishIn(AbstractEvent event)  { inBox.tryEmitNext(event); }
    public static void publishOut(AbstractEvent event) { outBox.tryEmitNext(event); }

    public static Flux<AbstractEvent> inBoxFlux()  { return inBox.asFlux(); }
    public static Flux<AbstractEvent> outBoxFlux() { return outBox.asFlux(); }
}
```

**核心设计：**
- **双通道架构**：`inBox`（入口，外部 → Agent）和 `outBox`（出口，Agent → 外部）
- **静态字段**：所有字段和方法都是 `static`，全局单例式访问
- **Sinks.Many multicast**：支持多订阅者
- **背压策略**：`onBackpressureBuffer(SMALL_BUFFER_SIZE * 10, false)` —— 缓冲区大小为 `Queues.SMALL_BUFFER_SIZE * 10`（Reactor 默认 SMALL_BUFFER_SIZE=256，所以缓冲区为 2560），第二个参数 `false` 表示缓冲区满时**不自动取消**（autoCancel=false）

### 2. 处理端（Session.start() 订阅 inBox）

`Session.start()`（`d:\project\autiva\autiva-desktop\src\main\java\cn\bitloom\agentic\session\Session.java:138-160`）：

```java
this.subscription = EventBus.inBoxFlux()
    .filter(event -> event.getSessionId().equals(this.id))   // 按会话 ID 过滤
    .concatMap(event -> {
        if (event instanceof MessageEvent messageEvent && messageEvent.isUserMessage()) {
            UserMessage userMessage = EventConverter.toUserMessage(messageEvent);
            if (this.getRespType() == SessionRespTypeEnum.STREAM) {
                return this.agent.runStream(this, userMessage)
                    .map(msg -> EventConverter.fromMessage(this.getId(), msg))
                    .doOnNext(EventBus::publishOut)          // 流式片段发布到 outBox
                    .doOnComplete(() -> this.setSessionState(SessionState.IDLE));
            } else {
                AssistantMessage am = this.agent.runBlock(this, userMessage);
                EventBus.publishOut(EventConverter.fromMessage(this.getId(), am));
                this.setSessionState(SessionState.IDLE);
                return Flux.empty();
            }
        } else {
            return Flux.just(event);   // 非 MessageEvent 直接透传（但目前不存在这种情况）
        }
    })
    .subscribe();
```

**关键设计点：**
- 使用 `filter` 按 `sessionId` 隔离不同会话的事件
- 使用 `concatMap`（而非 flatMap）保证**顺序处理**，避免并发执行
- **只处理 USER 类型**的 MessageEvent，其他类型透传（但当前没有其他类型进入 inBox）
- STREAM 模式：Agent 流式输出 → 每个片段通过 `EventConverter.fromMessage` 转换 → `EventBus.publishOut` 发布
- BLOCK 模式：Agent 阻塞返回单条 AssistantMessage → 转换后一次性发布

## 五、事件类型扩展点

### 如何添加新的事件类型

**方式 1：扩展 MessageEvent 的 Type 枚举（推荐用于消息类事件）**

1. 在 `MessageEvent.Type` 中新增枚举值（如 `SYSTEM`）
2. 在 `MessageEvent` 中添加对应字段和静态工厂方法
3. 在 `EventConverter.fromMessage` 中添加新的 Spring AI Message 类型分支（如需）
4. 在 `Session.start()` 的 `concatMap` 中添加对新类型的处理分支
5. 在 `HomePageViewModel.processEvent` 中添加处理分支

**方式 2：新增 AbstractEvent 子类（用于非消息类事件）**

1. 创建 `XxxEvent extends AbstractEvent`，使用 `@SuperBuilder`
2. 在 `Session.start()` 的 `concatMap` 中添加 `else if (event instanceof XxxEvent)` 分支
3. 在订阅者（HomePageViewModel 等）的 `doOnNext` 中添加 `instanceof` 判断

**注意**：由于 EventBus 的泛型是 `Sinks.Many<AbstractEvent>`，新事件类型会自动通过现有 inBox/outBox 通道传输，**无需修改 EventBus 本身**。

### 当前扩展点的限制

1. **EventConverter 是单向的**：只有 `toUserMessage` 反向方法，没有 `toAssistantMessage`/`toToolResponse`。如果需要从 MessageEvent 重建完整的 Spring AI Message 列表（如回放历史），需要补充反向转换方法。
2. **Session.start() 硬编码了 USER 类型处理**：其他类型会被 `return Flux.just(event)` 透传到下游订阅者，但不会触发 Agent 执行。
3. **outBox 是全局共享的**：所有会话的输出都通过同一个 outBox，订阅者需要自己按 `sessionId` 过滤（但当前 HomePageViewModel 没有过滤，依赖切换 session 时重新订阅）。

## 六、EventBus 静态字段和方法的线程安全性分析

### 1. 静态字段初始化的线程安全性

```java
public static Sinks.Many<AbstractEvent> inBox = Sinks.many()
        .multicast().onBackpressureBuffer(Queues.SMALL_BUFFER_SIZE * 10, false);
```

- **字段是 `public static`，非 `final`**：这是一个**潜在风险**。字段在类加载时初始化（JVM 类加载机制保证线程安全），但因为是 `public` 且非 `final`，**外部代码可以重新赋值**，导致订阅者丢失。建议改为 `public static final`。
- **Sinks.many().multicast()** 本身是线程安全的：Reactor 的 `Sinks.Many.multicast()` 返回的 Sink 内部使用线程安全的数据结构，`tryEmitNext()` 可以从多个线程并发调用。

### 2. 静态方法的线程安全性

```java
public static void publishIn(AbstractEvent event) {
    inBox.tryEmitNext(event);
}
```

- **`tryEmitNext()` 是线程安全的**：Reactor Sinks 的 `tryEmitNext` 方法设计为支持多线程并发发布，返回 `EmitResult` 表示发布结果。
- **但代码忽略了返回值**：`tryEmitNext` 返回 `EmitResult`，可能返回 `FAIL_OVERFLOW`（缓冲区满）、`FAIL_CANCELLED`（已取消）、`FAIL_TERMINATED`（已终止）等。当前代码**直接丢弃返回值**，意味着：
  - 缓冲区满时事件会**静默丢失**
  - Sink 被取消后发布的事件会**静默丢失**
  - 建议至少记录日志，或使用 `emitNext` + `EmitFailureHandler` 处理失败情况

### 3. 订阅的线程安全性

- **`inBoxFlux()` / `outBoxFlux()`** 返回的 `Flux` 是线程安全的，支持多线程订阅。
- **multicast 模式**：多个订阅者会共享同一个 Sink，每个订阅者独立维护自己的背压和缓冲。
- **autoCancel=false**：即使所有订阅者都取消，Sink 也不会自动终止，避免后续订阅者无法接收历史事件（但 multicast 本身不缓存历史，新订阅者只能收到订阅后的新事件）。

## 一、Claude Code 的记忆管理机制

### 核心架构：4 层记忆栈 + 操作系统式分页

Claude Code 采用**类操作系统虚拟内存分页**的设计哲学，将记忆分为 4 层由远及近的栈结构：

| 层级 | 载体 | 作用 | 加载时机 |
|---|---|---|---|
| 第 0 层（企业级） | `/Library/Application Support/ClaudeCode/CLAUDE.md` | 企业标准、安全策略 | 启动时强制加载 |
| 第 1 层（全局） | `~/.claude/CLAUDE.md` | 用户全局偏好 | 启动时全量加载 |
| 第 2 层（项目） | `./CLAUDE.md` | 项目技术栈、规范、命令 | 启动时全量加载，提交 Git |
| 第 3 层（本地） | `./CLAUDE.local.md` | 个人项目偏好 | 启动时加载，不提交 Git |
| 第 4 层（自动） | `~/.claude/projects/<项目>/memory/` | Claude 自主笔记 | 启动时加载 MEMORY.md 前 200 行 |

### 关键设计要点

**1. 双系统并存：手动 + 自动**
- **CLAUDE.md（手动记忆）**：开发者编写的静态指令，类似"宪法"，全量加载
- **MEMORY.md（自动记忆）**：Claude 自主做笔记，包含调试经验、踩坑记录、用户纠正
- **Auto Dream（自动整理）**：后台"垃圾回收"子进程，距离上次清理超过 24 小时且有 5+ 新会话时触发，合并冲突记忆、删除无效笔记，将 MEMORY.md 索引压缩到 200 行以内

**2. 工具驱动的"缺页中断"**
- 系统提示词只装**元数据和寻址指针**（路由表），不装业务逻辑
- Agent 评估当前上下文缺失时，主动发起 `FileRead` 工具调用拉取具体文件
- 比传统向量 RAG 更精准（Deterministic），从根本上消灭注意力稀释

**3. 闭环的"脏页写回"**
- Claude 被赋予修改自身记忆的最高权限
- 遇到未知错误、学到新命令、收到用户纠正时，自主写入笔记
- 极致利用 Prompt Caching 前缀匹配，MEMORY.md 作为稳定顶部前缀常驻缓存

**4. 触发时机**
- 启动时：加载第 1-3 层全量 + 第 4 层索引
- 工作中：Claude 自主决定何时记忆（**主动写入**）
- 后台：Auto Dream 异步整理（**自动整理**，不阻塞主对话）


### 关键设计要点

- 区分 Action 和 Observation 类型事件
- 优先记录用户指令和 AI 最终输出
- 过滤系统状态变更等噪音
- 动态截断：根据内容重要性选择性保留

- 蒸馏：通过 heartbeat 或 cron 定期将 daily notes 提升到 MEMORY.md

## 三、Hermes Agent（NousResearch）的记忆架构

### 核心架构：三层记忆 + 技能系统 + 外部记忆提供者

**1. 三层记忆架构**

| 层级 | 载体 | 容量限制 | 作用 |
|---|---|---|---|
| 短期推理记忆 | Transformer 上下文 | 模型窗口 | 即时 prompt-response 循环 |
| 程序性技能文档 | `~/.hermes/skills/*.md` | 无硬限制 | 持久化 markdown，捕获重复任务的解决方案 |
| 上下文持久层 | 向量存储 | 无限制 | 索引技能文档，支持自然语言检索 |

**2. 内置持久记忆（MEMORY.md + USER.md）**

| 文件 | 用途 | 字符限制 |
|---|---|---|
| `MEMORY.md` | Agent 个人笔记（环境事实、约定、学到的东西） | 2,200 字符（~800 tokens） |
| `USER.md` | 用户画像（偏好、沟通风格、期望） | 1,375 字符（~500 tokens） |

### 关键设计要点

**1. 主动写入 + 硬上限强制约束**
- Agent 通过 `memory` 工具自主管理记忆：`add`、`replace`、`remove`
- **不自动压缩**：当写入会超限时，工具返回错误而非静默丢弃
- Agent 必须在同一轮内自己整理（合并或删除条目）后重试
- 这迫使 Agent 主动思考记忆价值，而非依赖系统兜底

**2. 冻结快照模式（Frozen Snapshot）**
- 会话开始时，记忆作为冻结块注入系统提示词
- **会话中不更新系统提示词**：保留 LLM 前缀缓存性能
- 工具响应始终显示实时状态
- 记忆变更立即持久化到磁盘，但下次会话才在系统提示词中生效

**3. 技能系统（程序性记忆）**
- 遵循 agentskills.io 开放标准
- Markdown 驱动的程序性记忆，渐进式加载
- 任务后自动提炼新技能（自进化）
- 支持版本控制、注释、链接，形成知识图谱

**4. 外部记忆提供者插件（8 种）**
- Honcho、mem0、hindsight、holographic、retaindb、byterover、supermemory、openviking
- **自动行为**：
  - 注入提供者上下文到系统提示词
  - 每轮前**后台非阻塞**预取相关记忆
  - 每轮后同步对话到提供者
  - 会话结束时提取记忆
  - 镜像内置记忆写入到外部提供者
- 内置记忆与外部提供者**叠加**工作，不替代

**5. Honcho 辩证用户建模**
- 双层上下文注入：基础层（会话摘要 + 表征 + peer card）+ 辩证补充层（LLM 推理）
- 三个正交配置旋钮：`contextCadence`（基础层刷新频率）、`dialecticCadence`（LLM 调用频率）、`dialecticDepth`（推理深度 1-3）

## 四、MemGPT / Letta 的记忆分层设计

### 核心架构：OS 启发的双层虚拟上下文管理

MemGPT 是记忆系统设计的**奠基性方案**，将 LLM 视为操作系统，上下文窗口视为 RAM，外部存储视为磁盘。

```
┌─────────────────────────────────────────────────┐
│ Main Context（主上下文 = RAM）                    │
│  ├── System Instructions（系统指令，不可变）       │
│  ├── Core Memory / Memory Blocks（核心记忆）      │
│  │    ├── persona（AI 人设与状态）                │
│  │    └── human（对用户的核心认知）               │
│  └── Recent Messages（FIFO 对话队列）             │
├─────────────────────────────────────────────────┤
│ External Context（外部上下文 = 磁盘）              │
│  ├── Recall Memory（回忆记忆）                    │
│  │    └── 完整历史，conversation_search 检索      │
│  └── Archival Memory（归档记忆）                  │
│       └── 向量存储，archival_memory_search 检索   │
└─────────────────────────────────────────────────┘
```

### 关键设计要点

**1. 自编辑记忆（Self-Editing Memory）—— 核心创新**
- LLM 通过函数调用**主动管理自己的记忆**
- 工具集：
  - `memory_insert` / `core_memory_append`：插入核心记忆
  - `memory_replace` / `core_memory_replace`：替换核心记忆
  - `memory_rethink`：完全重写记忆块
  - `archival_memory_insert`：存储长期事实
  - `archival_memory_search`：语义查询归档
  - `conversation_search`：搜索历史对话

**2. 虚拟内存分页机制**
- **缺页中断（Page Fault）**：当上下文缺失信息时，LLM 主动调用工具拉取
- **脏页写回（Write-Back）**：LLM 判断信息重要时，主动写入核心记忆
- **页面淘汰（Eviction）**：FIFO 队列满时，旧消息被驱逐到 Recall Memory
- **递归摘要**：驱逐时生成递归摘要（前次摘要 + 被驱逐消息），保留要点

**3. Memory Blocks（记忆块）—— 核心原语**
- 标记化的持久字符串，Agent 每轮可见
- 常规块：`human`（用户认知）、`persona`（AI 自我描述）
- 自定义块：任务状态、项目状态等
- Agent 在正常循环中通过工具编辑

**4. 上下文窗口自动管理**
- 上下文满时，Letta 自动：
  - 将旧消息压缩为递归摘要
  - 移动完整历史到 recall 存储
  - Agent 可用 `conversation_search` 检索
- **透明发生**，Agent 维持连续性

**5. Sleep-time Compute / Heartbeat**
- 后台心跳机制，支持定时事件触发
- 异步记忆处理和更新
- 支持复杂多步骤任务

**6. 触发时机**
- 记忆写入：**Agent 主动决定**（主动写入）
- 记忆召回：**Agent 主动查询**（非系统自动注入）
- 上下文压缩：**系统自动触发**（接近窗口上限时）
- 压缩是**同步的**，发生在主对话循环内

## 五、Cursor / Windsurf 的上下文管理策略

### Cursor：显式控制 + 向量检索

**1. 上下文构建策略**
- **显式 @ 引用**：`@file`、`@folder`、`@codebase` 用户精确指定
- **向量索引**：项目索引到向量存储，强调注释和文档字符串
- **两阶段检索**：
  1. 向量搜索找候选片段
  2. AI 重新排序结果
- **.cursorrules**：项目级持久化 AI 行为规范

**2. 系统提示组织**
- 使用 `<communication>`、`<tool_calling>` 等标签结构化
- 明确行为指令：不道歉、先解释再执行、避免聊天中输出代码
- 上下文学习：通过范例"培训" AI

**3. ReAct 循环 + 专家混合**
- 循环：选择工具 → 说明意图 → 调用工具 → 查看结果 → 决定下一步
- 特殊差异语法：语义补丁 + 应用模型合并更改
- 沙盒环境运行实验代码
- 专家混合：大模型决策，小模型执行

### Windsurf：自动感知 + Cascade Flow

**1. 自动 Context 感知（与 Cursor 核心差异）**
- **Supercomplete 引擎**：AI 自己决定看什么
- 综合信号：光标位置、近期编辑历史、符号引用图（import、调用链）
- 自动引入相关文件，实现"仓库范围意识"
- **上下文固定（Context Pinning）**：像公告板，确保 AI 始终可见重要笔记

**2. Cascade 模式**
- **计划 + 审批**：生成改动计划 → 请求用户批准 → 执行 → 分析结果
- 持久化 Flow：跨多文件、多步骤维持上下文
- 可串联 20+ 工具调用，无需人工干预
- 自动响应用户编辑（参数变动后自动更新引用点）

**3. 记忆系统**
- AI 规则（自定义指令）+ 记忆系统（持久上下文）结合
- 跨会话记忆：返回项目时记住之前上下文
- 上下文压缩策略确保关注最相关内容

### 对比总结

| 维度 | Cursor | Windsurf |

| 记忆持久化 | .cursorrules + Chat History | Cascade Flow + 内置记忆 |
| Agent 模式 | 线性"计划→执行" | 响应式持续感知 |
| 模型灵活性 | 广泛（GPT-5、Claude 4.5 等） | 有限 |
| 适合场景 | 短会话、精确控制 | 长会话、自主执行 |

### 模式 1：OS 启发的虚拟内存分页（MemGPT 首创，Claude Code 工程化）

- Agent 通过工具主动管理记忆

- 不自动压缩，迫使 Agent 自整理
- **适用于**：需要高质量记忆、避免记忆膨胀

- 系统提示词冻结，保留前缀缓存
- 后台非阻塞预取相关记忆
- 工具响应显示实时状态
- **适用于**：性能敏感的长会话

### 模式 5：可插拔压缩器（OpenHands）
- NoOp / LLM 摘要 / DAG 无损 / 自定义
- 通过 `keep_first` 保留关键上下文
- **适用于**：需要灵活权衡成本与质量的场景

- 索引文件（MEMORY.md）+ 主题文件 + 原始日志

- **适用于**：文件系统友好的开发工具

### 模式 7：技能文档即程序性记忆（Hermes）

- 遵循开放标准（agentskills.io）

- **适用于**：需要自进化的智能体

# Claude Code 子智能体设计机制研究报告

基于对 Claude Code 官方文档（code.claude.com/docs/en/sub-agents）、Anthropic 官方博客、SDK 文档以及多篇深度技术解析的调研，以下是关于 Claude Code 子智能体设计机制的完整分析。

---

## 一、Claude Code 子智能体的上下文/会话处理

### 1.1 上下文隔离的核心原则

**子智能体不共享主智能体的对话历史。** 这是 Claude Code 设计中最核心、最强调的原则。

官方文档（[code.claude.com/docs/en/sub-agents](https://code.claude.com/docs/en/sub-agents)）明确表述：

> "Each subagent runs in its own context window with a custom system prompt, specific tool access, and independent permissions."
>
> "Each subagent starts fresh, unburdened by the history of the conversation or invoked skills."

官方博客（[claude.com/blog/subagents-in-claude-code](https://claude.com/blog/subagents-in-claude-code)）进一步说明：

> "A subagent is an isolated Claude instance with its own context window. It takes a task, does the work, and returns only the result. Think of subagents as the browser tabs of a Claude Code session: a place to chase a tangent without losing the main thread."

### 1.2 独立上下文窗口

- **子智能体拥有完全独立的上下文窗口**，与主智能体完全隔离
- 子智能体启动时是"fresh and empty"状态——没有主对话历史、没有已读取的文件、没有已加载的 skills
- 子智能体只接收两样东西：
  1. **自定义系统提示词**（来自 agent.md 文件的 markdown body）
  2. **委派消息（delegation brief）**——主智能体写的简短任务描述

### 1.3 子智能体执行完毕后的上下文处理

**子智能体的中间上下文直接丢弃，只返回最终摘要。**

这是设计的关键点（来自 [juejin.cn/post/7632902755376644096](https://juejin.cn/post/7632902755376644096) 的机制拆解）：

```
父 Agent (messages[])
├── User: "重构这个模块，先弄清楚测试框架"
├── Assistant: tool_use: task
│   └── 子 Agent (sub_messages[] — 独立，用完即弃)
│       ├── User: "这个项目用什么测试框架？"
│       ├── Assistant: → bash cat package.json (200行)
│       ├── Assistant: → bash cat jest.config.js (30行)
│       ├── Assistant: → bash ls tests/ (15行)
│       └── Assistant: "项目使用 Jest 测试框架，配置在..."
│       ★ 整个 sub_messages[] 在这里丢弃
├── tool_result: "项目使用 Jest 测试框架，配置在..."  ← 只有摘要返回
└── Assistant: 好的，现在开始重构... (继续干净地工作)
```

**关键效果**：父 Agent 的 messages 里只多了一条 `tool_result`，内容是精炼的摘要。子智能体执行过程中的几百行中间输出全部消失。

### 1.4 结果如何返回给主智能体

- 子智能体完成后，**只返回一条消息**（single result message）给主智能体
- 这条消息作为 `tool_result` 注入主智能体的上下文
- 主智能体看不到子智能体的中间工具调用、推理过程、文件读取内容
- 官方文档原文："the subagent returns only the relevant results to the main conversation"

### 1.5 例外：持久化记忆（Persistent Memory）

虽然默认情况下子智能体每次调用都是全新的，但 Claude Code 提供了 **persistent memory** 机制（通过 frontmatter 的 `memory` 字段配置）：

- 可配置 `~/.claude/agent-memory/` 目录
- 子智能体可以跨会话积累洞察（如代码库模式、反复出现的问题）
- 这是显式 opt-in 的功能，不是默认行为

## 二、Task 工具机制

### 2.1 Task 工具如何启动子智能体

Claude Code 内部使用统一的 `AgentTool`（在 `tools/AgentTool/AgentTool.tsx` 中定义），工具名为 `'Agent'`，并保留 `'Task'` 作为别名（来自 [zhanghandong.github.io 的源码分析](https://zhanghandong.github.io/harness-engineering-from-cc-to-ai-coding/en/part6/ch20.html)）。

**动态 Schema 组合**——输入参数 schema 根据运行时条件动态构建：

```typescript
const baseInputSchema = z.object({
  description: z.string(),       // 3-5 词的任务描述
  prompt: z.string(),            // 任务详情
  subagent_type: z.string().optional(),  // 子智能体类型
  model: z.enum(['sonnet', 'opus', 'haiku']).optional(),
  run_in_background: z.boolean().optional()
});
```

启动流程（4 步）：
1. **触发阶段**：主智能体根据任务类型或用户指令匹配子智能体
2. **初始化阶段**：子智能体加载自身配置（工具权限、模型、系统提示），创建独立上下文窗口
3. **执行阶段**：子智能体独立多轮交互，无需主智能体干预
4. **结果反馈阶段**：子智能体返回摘要，自身上下文按需保存或销毁

### 2.2 子智能体的 Prompt 如何构建

子智能体的"prompt"由两部分组成：

1. **系统提示词**：来自 agent.md 文件的 markdown body（不含 Claude Code 主系统提示）
   - 官方文档："Subagents receive only this system prompt (plus basic environment details like working directory), not the full Claude Code system prompt."
2. **委派消息**：主智能体通过 `prompt` 参数传入的任务描述

**关键设计**：主智能体需要把情境压缩成一段书面简报（delegation brief），因为子智能体看不到主对话历史。这个简报是摘要，会丢失细节——这是 isolation 的代价。

### 2.3 中间状态可见性

- **默认不可见**：主智能体看不到子智能体的中间工具调用、推理过程
- **TaskCard/UI 可见**：Claude Code 的 Agent View 可以集中管理并行会话，观察运行中的子智能体
- **后台模式**：`run_in_background` 参数允许子智能体后台运行，主智能体可继续工作，之后通过 `TaskOutput` 工具检索结果

### 2.4 子智能体的记忆

- **默认无记忆**：每次调用都是全新的
- **持久化记忆（opt-in）**：通过 `memory` frontmatter 字段配置，可跨会话积累
- **Session 持久化**：SDK 文档提到"Subagent transcripts persist within their session. You can resume a subagent after restarting Claude Code by resuming the same session."
- **自动清理**：transcripts 根据 `cleanupPeriodDays` 设置（默认 30 天）清理

## 三、上下文隔离策略

### 3.1 默认策略：完全无状态（Stateless）

Claude Code 的默认设计是**子智能体每次调用都是全新的、无状态的**：

- 不继承父对话历史
- 不继承已加载的 skills
- 不继承已读取的文件内容
- 只接收系统提示 + 委派消息

### 3.2 三大硬约束（来自 [CSDN 深度解析](https://blog.csdn.net/2401_87662859/article/details/161256712)）

1. **子代理获得全新上下文，而非共享历史**
   - 替代方案的致命缺陷："共享父代理完整上下文会给子代理更多信息，但也会用无关细节淹没它。上下文窗口是有限的，填充父历史会挤占子代理自身工作的空间；基于 fork 的复制上下文方案是折中方案，但仍会在无关历史上浪费大量 token。"

2. **Explore 类型子代理强制只读权限**（最小权限原则）

3. **子代理不能再创建子代理**（禁止递归委派）
   - `task` 工具不包含在子代理的工具集中
   - 防止无限委派循环

### 3.3 主智能体如何避免被污染

主智能体的上下文保护通过以下机制：

1. **单向通信**：子智能体只返回一条摘要消息，中间过程全部丢弃
2. **tool_result 摘要**：子智能体的完整对话历史直接丢弃，父代理只保留最终摘要
3. **并行隔离**：多个子智能体并行运行时，各自独立上下文，互不干扰
4. **AsyncLocalStorage 上下文隔离**：同一进程内多个 Agent 并发时，使用 Node.js 的 `AsyncLocalStorage` 隔离身份信息（[源码分析](https://zhanghandong.github.io/harness-engineering-from-cc-to-ai-coding/en/part6/ch20.html)）

### 3.4 例外：Fork 模式（实验性）

Claude Code 提供了一个**实验性的 Fork 模式**（需 v2.1.117+，通过 `CLAUDE_CODE_FORK_SUBAGENT=1` 启用）：

官方文档（[Fork the current conversation](https://code.claude.com/docs/en/sub-agents#fork-the-current-conversation)）：

> "This drops the input isolation that subagents otherwise provide: a fork sees the same system prompt, tools, model, and message history as the main session, so you can hand it a side task without re-explaining the situation. The fork's own tool calls still stay out of your conversation and only its final result comes back, so your main context window stays clean."

**Fork 模式的关键特点**：
- Fork 继承主会话的**完整对话历史**（系统提示、工具、模型、消息历史）
- Fork 自己的工具调用仍然不会污染主会话——**隔离是单向的**
- 主要用于 general-purpose agent（Named subagents 如 Explore 仍然按原方式 spawn）
- **成本优势**：由于 fork 的系统提示和工具与父级相同，首次请求可复用父级的 prompt cache，使 forking 比 spawning fresh subagent 更便宜

来自 [amitkoth.com 的分析](https://amitkoth.com/claude-code-general-purpose-agent/)：

> "A fork is a subagent that inherits the entire conversation so far, rather than starting fresh... The isolation it keeps is one-directional: the fork's own tool calls and file reads stay out of your conversation, so your main context still does not fill with debris, but the fork itself is not working blind."

**Fork vs 命名子智能体的区别**（官方文档）：

| 维度 | 命名子智能体（Named Subagent） | Fork |
|------|------|------|
| 上下文 | 全新、空 | 继承主会话完整历史 |
| 系统提示 | 自定义 | 与主会话相同 |
| 工具 | 可自定义 | 与主会话相同 |
| 隔离 | 双向完全隔离 | 单向（fork 的输出不污染主会话） |
| 适用场景 | 窄域专家任务 | 需要完整上下文的复杂、深度上下文相关任务 |
| 成本 | 需要写 delegation brief | 复用 prompt cache，更便宜 |

## 四、与 Autiva 当前设计的对比

### 4.1 Autiva 当前实现

查看 `d:\project\autiva\autiva-desktop\src\main\java\cn\bitloom\agentic\session\FileSystemSessionManager.java` 的 `fork()` 方法（第 230-271 行）：

```java
public Session fork(String parentSessionId, String subagentName) {
    // ...
    if (parentSession != null && !parentSession.getMessages().isEmpty()) {
        List<Message> parentMessages = parentSession.getMessages();
        int lastUserMsgIndex = -1;
        for (int i = parentMessages.size() - 1; i >= 0; i--) {
            if (parentMessages.get(i).getMessageType() == MessageType.USER) {
                lastUserMsgIndex = i;
                break;
            }
        }
        if (lastUserMsgIndex >= 0) {
            List<Message> inherited = new ArrayList<>(parentMessages.subList(
                lastUserMsgIndex, parentMessages.size() - 1));
            childSession.getMessages().addAll(inherited);
        }
    }
    // ...
}
```

**Autiva 当前行为**：
- Fork 时继承父会话**从最后一条用户消息到倒数第二条**的消息
- 这是一种"部分继承"——只继承最近一轮对话上下文
- `TaskTool.execute()` 中，每次调用子智能体都会调用 `fork()`（除非 resume）

### 4.2 与 Claude Code 设计的对比

| 维度 | Claude Code 默认（Named Subagent） | Claude Code Fork 模式（实验性） | Autiva 当前设计 |
|------|------|------|------|
| **上下文继承** | 不继承（fresh & empty） | 继承完整对话历史 | 继承最近一轮对话（部分继承） |
| **默认行为** | 默认即此模式 | 需显式启用 `CLAUDE_CODE_FORK_SUBAGENT=1` | fork 是默认且唯一机制 |
| **隔离方向** | 双向完全隔离 | 单向（子输出不污染父） | 单向（子会话独立持久化） |
| **delegation brief** | 必须（主智能体写摘要） | 不需要（继承完整上下文） | 不需要（继承部分上下文） |
| **成本** | 需要写 brief，但子上下文干净 | 复用 prompt cache，更便宜 | 继承部分历史，折中 |
| **适用场景** | 窄域专家、研究类任务 | 复杂深度上下文任务 | 所有子智能体调用 |

### 4.3 设计合理性评估

**Autiva 当前设计的问题**：

1. **违反了 Claude Code 的核心设计原则**：Claude Code 强调子智能体"starts fresh, unburdened by the history"，而 Autiva 默认继承父会话消息。这会导致：
   - 子智能体被无关历史干扰
   - Token 浪费在无关历史上
   - 失去"干净上下文 = 聚焦分析"的优势

2. **部分继承是折中方案，但 Claude Code 明确批评这种方案**：
   > "基于 fork 的复制上下文方案是折中方案，但仍会在无关历史上浪费大量 token。"

3. **缺少两种模式的区分**：Claude Code 明确区分了两种场景：
   - 窄域专家任务 → 全新上下文（默认）
   - 深度上下文相关任务 → Fork 模式（opt-in）
   
   Autiva 当前一刀切使用 fork，没有区分。

4. **继承范围不明确**：Autiva 只继承"最后一条用户消息到倒数第二条"，这个范围的合理性存疑——为什么不是完整历史？为什么不是完全不继承？

### 4.4 改进建议

参考 Claude Code 的设计，建议 Autiva 考虑：

1. **提供两种模式**：
   - **默认模式（Fresh）**：子智能体不继承父会话消息，只接收 system prompt + delegation brief
   - **Fork 模式（opt-in）**：继承完整父会话历史，用于深度上下文相关任务

2. **让子智能体类型决定模式**：
   - Explore/Plan 等研究类子智能体 → Fresh 模式
   - general-purpose 等需要上下文的子智能体 → 可选 Fork 模式

3. **如果保持当前 fork 设计**，应明确文档化这是"Fork 模式"语义，并考虑：
   - 继承完整历史而非部分历史（与 Claude Code Fork 模式一致）
   - 利用 prompt cache 降低成本
   - 明确这是 opt-in 行为而非默认

## 五、关键结论

1. **Claude Code 的核心设计是"上下文隔离"**：子智能体默认不共享主智能体对话历史，拥有独立上下文窗口，执行完毕后中间上下文丢弃，只返回摘要。

2. **Task 工具是统一入口**：通过 `AgentTool`（别名 `Task`）启动子智能体，参数包括 description/prompt/subagent_type/model/run_in_background。

3. **Fork 模式是例外而非默认**：Claude Code 提供实验性 Fork 模式继承完整历史，但这是 opt-in 的，且主要用于 general-purpose agent。

4. **Autiva 当前设计偏离了 Claude Code 的主流设计**：Autiva 默认通过 `fork()` 继承父会话消息，这更接近 Claude Code 的实验性 Fork 模式，而非默认的 Fresh 模式。建议区分两种模式，让子智能体类型决定使用哪种上下文策略。

### Spring AI 1.1.7 的能力说明（基于公开 API 知识）

由于本地 Maven 仓库（`C:\Users\TRS\.m2\repository`）中未找到 Spring AI 1.1.7 的 jar 包（项目可能未执行过 `mvn` 构建），无法直接查看源码。但基于 Spring AI 1.1.x 的公开 API：

- **`ChatResponse.getMetadata()`** 返回 `ChatResponseMetadata`，其中包含 `getUsage()` 方法返回 `Usage` 对象
- **`Usage` 接口**（`org.springframework.ai.chat.metadata.Usage`）主要包含：
  - `getPromptTokens()` — 输入 token 数
  - `getCompletionTokens()` — 输出 token 数

- **`OpenAiChatOptions`** 提供 `maxTokens()`/`maxCompletionTokens()` 方法，但这是**请求参数**（限制单次响应的最大输出 tokens），**不是模型的上下文窗口容量**
- Spring AI 1.1.x **没有提供标准的 API 来获取模型的 max context tokens**，因为不同提供商对此的支持差异很大，且通常需要硬编码或查询模型信息接口

```java
private static int estimateLength(List<Message> messages) {
    int length = 0;
    for (Message msg : messages) {
        String text = msg.getText();
        if (text != null) {
            length += text.length();  // 直接使用字符长度
        }
        if (msg instanceof AssistantMessage am && !am.getToolCalls().isEmpty()) {
            length += am.getToolCalls().size() * 200;  // 每个工具调用估算 200 字符
        }
        if (msg instanceof ToolResponseMessage) {
            length += 500;  // 每个工具响应估算 500 字符
        }
    }
    return length;
}
```

## 总结

### 核心结论

1. **Spring AI 1.1.7 不提供标准的 max context tokens API**：
   - `Usage` 接口只包含本次请求的实际用量（`prompt_tokens`、`completion_tokens`、`total_tokens`），**不包含模型的上下文窗口上限**
   - `OpenAiChatOptions.maxTokens()` 是请求参数（限制单次输出），不是上下文窗口容量
   - `ChatResponse.getMetadata().getUsage()` 可获取用量，但项目中未使用

2. **项目未存储 max context tokens 信息**：
   - `ModelTypeEnum` 仅是枚举标识，无任何字段
   - `ModelFactory` 构建模型时不设置上下文相关参数
   - 配置文件中无 max context tokens 配置项

3. **项目采用字符数估算替代 token 计数**：
   - `Session.contextCapacity = 40000` 字符（非 tokens）
   - `CompactChatMemory.estimateLength()` 用字符长度估算
   - `MemoryCompactAdvisor` 在达到 50% 容量时触发压缩
   - **不引入 tokenizer 依赖**（见 `d:\project\autiva\autiva-desktop\src\main\java\cn\bitloom\agentic\memory\AGENTS.md` 第 99 行注意事项）

4. **DeepSeek 配置**：
   - 默认模型 `deepseek-chat`，实际路由到 DeepSeek V4（`deepseek-v4-flash`）
   - 项目中未硬编码 DeepSeek-V3/V4 的实际上下文窗口大小（64K/128K tokens）

## 6. 工具之间的状态共享需求

### TaskTool 与 TaskOutputTool 之间的状态共享 —— **存在 bug**

**设计意图**：TaskTool 创建后台任务后返回 `task_id`，用户通过 TaskOutputTool 用该 `task_id` 检索结果。两者需要共享 `TaskRepository`。

**当前实现**：
- `TaskOutputTool`（Toolkit.java:203-204）：使用 `new DefaultTaskRepository()` —— 每次构建工具时 new 一个新实例
- `TaskTool`（Toolkit.java:121-129）：Builder 中**没有设置 taskRepository**，所以 `taskRepository` 字段为 null

**后果**：
1. TaskTool 的 `taskRepository` 为 null，调用 `this.taskRepository.putTask()` 会抛 NPE
2. 即使 TaskTool 有 taskRepository，也与 TaskOutputTool 的不是同一个实例，状态无法共享

**修复方向**：`TaskRepository` 应该是 Spring Bean（`@Component`），由 Toolkit 注入并共享给 TaskTool 和 TaskOutputTool。

### CommandTool 与 ProcessTool 之间的状态共享

**设计意图**：CommandTool 启动后台进程后返回 `session_id`，用户通过 ProcessTool 用该 ID 管理进程。

**当前实现**：
- `CommandTool`（Toolkit.java:190）：`CommandTool.builder().build()` —— Builder 内部默认 `new ProcessManager()`
- `ProcessTool`（Toolkit.java:191）：`ProcessTool.builder().build()` —— Builder 内部默认 `new ProcessManager()`

**后果**：两者使用**不同的 ProcessManager 实例**，CommandTool 启动的后台进程无法被 ProcessTool 管理。

**修复方向**：`ProcessManager` 应该是 Spring Bean，由 Toolkit 注入并共享。

### 其他工具的状态共享

- `MemorySaveTool/UpdateTool/DeleteTool/SearchTool`：都通过构造函数注入同一个 `memoryManager`（Spring Bean），**状态共享正确**
- `CronCreateTool/ListTool/DeleteTool/TriggerTool`：都注入同一个 `cronManager`（Spring Bean），**状态共享正确**
- `SkillTool` 和 `SkillConfigXxxTool`：都注入同一个 `skillManager`，**状态共享正确**
